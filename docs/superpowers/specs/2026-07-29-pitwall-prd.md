## 0. 한 줄 정의

**LiteLLM 프록시 로그를 8시간 내구 레이스 중계 화면으로 번역하는, 세컨드 모니터에 상시 띄워두는 앰비언트 디스플레이.**

제품명 `PITWALL`은 F1에서 팀이 앉아 전체 레이스를 감시하는 벽을 가리킨다. 관제와 관전이 같은 자리에서 일어난다는 이 제품의 성격과 정확히 일치한다.

## 1. 이것은 대시보드가 아니다

이 선언이 PRD 전체를 지배한다. 이후 모든 결정은 여기서 파생된다.

대시보드는 **응시하는 물건**이다. 그리고 대부분 실패한다 — 평균 체류 7초, 실패 원인 1위는 인지 과부하, 그리고 "데이터가 보여줄 수 있는 것"을 보여주고 "알아야 할 것"은 안 보여준다는 구조적 결함.

PITWALL은 **곁눈질하는 물건**이다. 학술적으로는 앰비언트/글랜서블 디스플레이라는 별도 카테고리에 속한다 — 인간의 전주의적 처리(preattentive processing)를 활용해, 전경 작업에서 주의를 빼앗지 않으면서 정보를 흡수시키는 정보 기기.

**이 구분이 성공 지표를 바꾼다.** 체류 시간이 길면 실패다. 3초 훑고 자기 일로 돌아가되, 내일도 켜져 있으면 성공이다.

시장 증거 **[Medium]**: Claude Code 사용량 대시보드는 이미 포화 상태(`claude-usage` 2,084★, `claude-swap` 1,406★, `sniffly` 1,252★, `TokenTracker` 1,124★ — 2026-07-29 실측)이며 전부 차트 그리드다. 그런데 기능이 가장 적은 `Clawdmeter`(ESP32 데스크 장치, 1,932★)가 이 목록 내 2위다. 사람들은 쓸모가 아니라 **책상에 두고 싶은 물건**에 반응한다.

`racing metaphor monitoring`, `agent race visualization`, `observability gamification` GitHub 검색 결과는 0건 — 화이트스페이스다. **다만 이는 "아무도 안 했다"의 증거이지 "하면 된다"의 증거가 아니다.** 아무도 안 한 이유가 수요 부재일 가능성을 §3.2 반증 지표로 감시한다.

> **7초 체류 통계의 출처는 마케팅 블로그이며 학술 근거가 아니다. [Low]** 다만 이 절의 결론(앰비언트 vs 대시보드 구분)은 Gartner의 앰비언트/글랜서블 디스플레이 정의라는 별도 근거로 지지되므로 결론 자체는 유지한다.

## 3. 성공 지표 및 반증 지표

### 3.1 성공 지표 (4주차 측정)

| 지표 | 목표 |
|---|---|
| 주 3일 이상 실행하는 사용자 비율 | ≥ 40% |
| 1인당 일평균 정상 실행·가시 상태 시간 | ≥ 2시간 |
| 라디오 인사이트 유용성 응답 | ≥ 30% |

### 3.2 반증 지표 (하나라도 관측되면 설계 재검토)

> 30년차 규칙: 성공 지표만 있는 PRD는 성공만 보고한다. 반증 지표를 같은 무게로 박아둔다. 정상 실행·가시 상태 시간은 실제 응시 시간이 아니며, 앰비언트 품질은 3초 인지 정확도와 재방문율로 판단한다.

- 익명 해제·실명 공개 요청이 발생한다 → **감시 도구화 시작 신호**
- "누가 토큰 많이 썼네" 류 발언이 관측된다 → **의도치 않은 경쟁 유발**
- 2주차 이후 일평균 정상 실행·가시 상태 시간이 1주차 대비 50% 이하로 감소 → **앰비언트 가설 실패**
- 라디오 피드백 유용성 < 10% → **인사이트 로직 폐기 검토**

## 4. 사용자 및 시나리오

### 4.1 페르소나

**P1 — 참여자 (주 사용자).** 조직 구성원. 자기 차가 트랙 위에 있다. 세컨드 모니터에 종일 띄워둔다. 자기 상태와 전체 분위기를 곁눈질한다.

**P2 — 관전자.** 데모·발표·사내 스크린. 개인 식별에 관심 없음. "이 조직이 AI를 이만큼 쓴다"는 인상을 받는다.

> **의도적으로 제외한 페르소나: 관리자.** "누가 얼마나 쓰나 보고 싶은" 사용자를 v1의 고객으로 삼지 않는다. 이 페르소나를 넣는 순간 G4가 무너진다.

### 4.2 핵심 시나리오

**S1 — 아침 그리드.** 근무 시작 5분 전(기본 08:55), 화면에 포메이션 랩. 근무 시작 정각(기본 09:00) 스타트 라이트 5→4→3→2→1→소등. 이미 활동 중인 차량이 출발. 아직 조용한 차량은 피트에 남는다.

**S2 — 곁눈질.** 14:00, 코딩 중 3초 시선 이동. 트랙이 붐빈다(조직이 바쁨), 내 차 연료 링이 30%(오늘 한도 70% 소진), 라디오에 노란 줄이 하나 떠 있다(누군가 에러). 시선 복귀.

**S3 — 라디오 인사이트.** 15:00 정시, 내 차에 라디오. "캐시 읽기 비율 12%. 같은 컨텍스트를 반복 전송하고 있음." 실제 행동이 바뀔 수 있는 유일한 접점.

**S4 — 체커기.** 17:55 "퇴근 5분 전" 콜. 18:00 체커기. 하루 요약 카드: 총 주행거리(토큰), 완주 여부, 클래스, 최고 연비 구간.

### 6.2 레이아웃 B — 위젯 메인 (v1.5 대안)

카메라 카드가 화면 대부분을 차지하고 트랙은 구석 미니맵으로 축소. **v1에서 구현하지 않되, 레이아웃 레이어를 교체 가능하게 설계한다.** 트랙 컴포넌트와 카메라 컴포넌트는 크기·위치에 대한 가정 없이 컨테이너 크기를 받아 렌더한다.

실제 방송도 디렉터가 상황에 따라 정보 밀도를 바꾼다 (`sab-f1-ui`의 타이밍 보드는 4가지 표시 모드를 갖는다). 모드 전환을 예외가 아니라 기본 전제로 둔다.

### 6.3 차량 글리프 — 리더 라이트 원칙

**밀도 문제의 해법은 르망에 이미 있다.** 2026년 르망은 62대가 3클래스(Hypercar / LMP2 / LMGT3)로 동시 주행하는데도 관중이 트랙사이드에서 식별한다. 방법은 라벨을 읽는 게 아니라 **차체 자체에 상태를 인코딩**하는 것이다 — 클래스별 발광 번호판 색상과 리더 라이트 시스템(측면 다이오드 3개, 점등 개수 = 클래스 내 순위).

> **인용 정정 [High].** v1.0은 LMP1 / LMP2 / LMP3 / GTE Pro / GTE Am 5클래스와 그 색상 체계를 인용했으나, 이는 폐지된 규정이다. LMP1은 2020년, GTE Pro는 2022년, GTE Am은 2023년에 종료되었고 LMGT3가 2024년부터 GTE를 대체했다. 참조한 기사가 구 규정 시절 글이었다.
>
> **[Unknown] 2026년 현행 클래스별 번호판 색상 값은 확인하지 못했다.** 따라서 특정 색상값을 규격으로 채택하지 않는다. 채택하는 것은 **원리**(클래스=색+형태, 순위=이산 마커, 라벨 없음)이지 특정 팔레트가 아니다. 실제 색상은 §6.3 접근성 제약과 자체 대비 검증으로 결정한다.
>
> 부수 효과: v1이 정한 3클래스(H/P/GT)가 현행 르망 3클래스(Hypercar/LMP2/LMGT3)와 정확히 일치한다. 설계는 무사하고 인용만 틀렸다.

PITWALL의 차량 글리프도 텍스트를 쓰지 않는다.

| 시각 채널 | 인코딩 | 비고 |
|---|---|---|
| 색상 (hue) | 클래스 (모델 티어) | 색각 이상 대비 필수 — 아래 참조 |
| 형태 (shape) | 클래스 (중복 인코딩) | 원 / 삼각 / 사각. 색만으로 구분 금지 |
| 외곽 링 채움 | 연료 잔량 (0–100%) | |
| 밝기 | 최근 활동 강도 | 유휴 시 감광 |
| 점멸 (1회 펄스) | 이벤트 발생 | 색상으로 종류 구분 |
| 크기 | **사용 안 함** | 밀도 문제 악화 |
| 텍스트 라벨 | **트랙 위에서는 사용 안 함** | 카메라에 잡혔을 때만 표시 |

> **접근성 하드 룰.** 색상 단독 인코딩 금지. 클래스는 색 + 형태 이중 인코딩.
>
> 유병률 **[Medium]**: 북유럽계 남성 7–8%, 동아시아계는 대체로 4–6%. 한국 대상 연구는 5.9%와 8.12%로 **출처 간 불일치**가 있다. 어느 수치를 택하든 200명 조직이면 색각 이상자가 최소 수 명 존재한다는 결론은 동일하므로, 이중 인코딩 규칙은 수치 확정과 무관하게 **[High]**로 유지한다.

### 6.4 트랙 위 밀도 관리

**활동 중인 차량만 트랙에 올린다.** 등록 인원 200명 중 동시 호출 중인 인원은 훨씬 적다. 유휴 차량은 피트로 내리고 카운터로만 표시한다. 추가 구현 비용 없이 트랙 위 밀도가 자연 조절된다.

**클래스별 레인 분리.** 르망 방식대로 트랙을 클래스별 레인으로 나눠 겹침을 분산한다.

**밀도 상한.** 한 레인에 렌더 상한(기본 40대)을 두고, 초과분은 클러스터 배지로 묶는다. 상한 도달 시 화면에 명시한다 — 조용한 truncation은 "전부 보여줬다"는 거짓말이 된다.

## 7. 데이터 모델

### 7.0 시간·설정 모델

제품 동작에 영향을 주는 값은 고정 상수가 아니라 설정으로 조정한다.

| 설정 | 기본값 | 조정 범위 |
|---|---:|---|
| 근무 시작 | 09:00 | 로컬 시각 |
| 근무 종료 | 18:00 | 로컬 시각 |
| 휴식 구간 | 12:00–13:00 | 0개 이상 구간 |
| 시간 배속 | 1× | 1× / 60× / 600× |
| 한도 경고 선행시간 | 60분 | 0분 이상 |
| 한도 경고 잔여 임계값 | 20% | 0–100% |
| 타이어 윈도우 | 5시간 | 데이터 소스 확정 전 시뮬레이터 전용 |

**레이스 시간은 설정이 아니라 파생값이다.**

```
레이스 시간 = 근무 종료 − 근무 시작 − Σ(휴식 구간)
기본값     = 18:00 − 09:00 − 1h = 8시간
```

> **v1.3 정정 [High].** v1.3은 `실제 레이스 시간`을 독립 설정으로 두었다. 근무 창과 휴식이 모두 설정인데 레이스 시간까지 따로 받으면 세 값이 서로 모순될 수 있다(09:00–18:00 · 휴식 0 · 레이스 8시간 → 1시간이 어디에도 속하지 않는다). 상단 바의 분모(§6.1 `⏱ 04:12:33 / 08:00`)와 경과 시간은 **항상 이 식으로 계산한다.** 휴식 구간은 경과 시간에 누산하지 않는다 — 점심에 시계가 멈춰야 "8시간 레이스"가 참이 된다.
>
> v1.2까지의 "8시간 = 09:00–18:00"은 산수 오류였다(9시간). v1.3이 이를 잡았고 v1.4가 계산 방식을 고정한다.

추가 조정 대상은 모델→클래스 매핑, 시뮬레이터 분포, 레인 렌더 상한, 카메라 슬롯 수·가중치, 하이라이트 종류, 모션·사운드·레이아웃이다. 각 값은 조직 기본값·사용자 로컬 설정·현재 세션 설정 계층으로 제공한다. 설정 변경은 다음 이벤트부터 적용하며, 이미 발생한 이벤트의 의미를 소급 변경하지 않는다.

설정 우선순위는 **조직 기본값 → 사용자 로컬 설정 → 현재 세션 설정**이다. 현재 세션 설정은 해당 레이스에만 적용한다.

#### 조정 불가 항목

아래는 설정으로 노출하지 않거나, 하한을 두고 그 아래로는 내릴 수 없다. **완화하면 제품이 죽는 규칙들이다.**

| 항목 | 규칙 |
|---|---|
| 프라이버시·접근성·본문 미수집·컬럼 화이트리스트 | 조정 불가 (§12) |
| 개인 차량 모드 최소 집계 인원 | **하한 10명. 상향만 가능** (§12.1) |
| 카메라 최소 노출 시간 / 재선별 쿨다운 / 슬롯 교체 간격 | **하한 8초 / 60초 / 3초. 상향만 가능** (§9.2) |
| 동일 유형 라디오 재발화 금지 간격 | **하한 30분. 상향만 가능** (§10.3) |
| 레인 렌더 상한 | **상한 40대. 하향만 가능** (§6.4 — 성능 예산 장치) |

> **v1.3 정정 [Medium].** v1.3은 카메라 쿨다운과 라디오 발화 쿨다운을 자유 조정 대상에 넣었다. §9.2는 깜빡임 방지 규칙이고 §10.3은 제목 자체가 "하드 제약"이다. 0으로 낮출 수 있으면 자동 선별 UI가 읽히지 않게 되고 라디오는 스팸이 된다. 조정을 허용하되 **방향을 한쪽으로만** 연다.

타이어 표시도 설정으로 제어한다. `off`가 기본값이며, `rolling_budget`(개인별 5시간 롤링 예산) 또는 `proxy_budget`(LiteLLM 자체 예산)만 선택할 수 있다. 실제 한도 데이터가 없는 모드에는 `ESTIMATE` 또는 `SIMULATED` 배지를 표시한다.

### 7.1 정규화 이벤트 스키마

프론트엔드가 소비하는 유일한 계약. 시뮬레이터와 실 LiteLLM 어댑터 모두 이 형태로 방출한다.

```typescript
type CarClass = 'H' | 'P' | 'GT';   // Hypercar / Prototype / GT — 모델 티어

interface CarEvent {
  ts: string;              // ISO8601
  car_id: string;          // HMAC(user_id, deployment_salt) — 원본 미보관
  car_number: number;      // 1–999, car_id에서 결정론적 파생. 표시용
  car_class: CarClass;
  model: string;           // 'claude-opus-5' 등
  kind: 'call' | 'error' | 'pit_in' | 'pit_out' | 'retire' | 'limit_warn';

  session_id?: string;     // SpendLogs.session_id — 세션 경계

  tokens: {
    prompt: number;
    completion: number;
    // cache_read / cache_write 는 per-request 로 존재하지 않는다. §7.2 참조
  };
  cache_hit: boolean;      // SpendLogs.cache_hit (String → boolean 정규화)
  cost_usd: number;
  latency_ms: number;      // SpendLogs.request_duration_ms
  ttft_ms?: number;        // completionStartTime − startTime

  status: 'ok' | 'error';
  error_code?: string;     // 어댑터 경계에서 허용된 오류 코드만 추출. 원본 metadata는 폐기

  fuel_pct: number;        // 0–100, 일간 예산 대비 잔여
  tyre_pct?: number;       // 0–100, 선택된 타이어 모드의 잔여. 기본 off
}

// 일 1회 집계 — LiteLLM_DailyUserSpend 계열에서만 얻어진다
interface CarDailyRollup {
  car_id: string;
  date: string;
  cache_read_input_tokens: number;
  cache_creation_input_tokens: number;
  prompt_caching_savings_spend: number;
  successful_requests: number;
  failed_requests: number;
}
```

**금지: 프롬프트·응답 본문은 이 스키마에 들어오지 않는다.** 라디오 메시지는 전부 메타데이터에서 생성한다. §10, PRIV-8 참조.

### 7.2.1 캐시 토큰 — G2에 직접 영향

`cache_read_input_tokens`와 `cache_creation_input_tokens`는 **`LiteLLM_SpendLogs`에 존재하지 않는다.** 일별 집계 테이블(`LiteLLM_DailyUserSpend` / `DailyTeamSpend` / `DailyAgentSpend` 등)에만 있다. `prompt_caching_savings_spend`, `compression_saved_tokens`도 같은 위치다.

**결과: §10.2 루틴 라디오의 캐시 규칙은 시간당 발화가 불가능하고 일단위로만 성립한다.**

선택지는 세 가지다.

1. **캐시 인사이트를 일 1회 "레이스 후 브리핑"으로 이동** — 가장 정직하고 구현이 단순. 하루 요약 카드(S4)에 자연스럽게 붙는다. **권장.**
2. 시간당에는 `cache_hit` 불리언 비율만 쓰고, 토큰 절감량은 일단위로 — 두 지표가 다르다는 걸 사용자가 혼동할 위험.
3. 어댑터가 자체 누적 — 프록시가 이미 하는 일을 중복 구현. 기각.

**v1.1 결정: 선택지 1.** §10.2에서 캐시 규칙을 제거하고 §10.5 일일 브리핑으로 이동한다.

### 7.2.2 5시간 윈도우 — 데이터 소스 불명 (신규 차단 조건)

**[High]** 구독제(Pro/Max)의 5시간 한도와 LiteLLM 프록시를 통한 API 사용량은 **서로 다른 과금 체계다.** 구독 한도 버킷은 Claude Code·claude.ai·Cowork가 공유하며, 프록시 로그에서 그 잔량을 알 방법이 없다.

따라서 "타이어 마모 = 5시간 리밋 잔여"는 **현재 데이터 소스가 없다.** 대안:

- (a) LiteLLM 자체 예산 기능(`budget_reset_at`)을 5시간 주기로 설정해 프록시 내부 한도로 대체
- (b) 타이어를 구독 한도가 아니라 **개인 일일 예산의 5시간 구간 소진율**로 재정의
- (c) v1에서 타이어 은유 삭제

**v1은 시뮬레이터이므로 진행에 지장 없으나, Q3를 v1.5 차단 조건으로 승격한다.**

### 7.2.3 인덱스 정정

v1.0은 2차 출처(DeepWiki)를 인용해 "`api_key`, `user`, `team_id`가 인덱스"라고 썼으나 **틀렸다.** `LiteLLM_SpendLogs`의 실제 인덱스는 `startTime`, `[startTime, request_id]`, `end_user`, `session_id` 뿐이다.

→ 개인별 실시간 폴링을 `user` 조건으로 돌리면 풀스캔이 될 수 있다. 반면 `LiteLLM_DailyUserSpend`에는 `[user_id, date]` 인덱스가 있다. **개인 집계는 일별 테이블, 실시간 스트림은 `startTime` 범위 스캔**이 올바른 접근이다. v1.5 성능 설계에 반영.

**BOX BOX 휴리스틱의 한계를 명시한다.** 마지막 호출 후 N초(기본 90초) 무호출 = 피트인으로 간주. 이 신호는 **사용자 입력 대기 / 자리 비움 / 로컬 툴 장기 실행**을 구분하지 못한다. UI에서 "대기 중"이라 단정하지 않고 중립적으로 `IN PIT`만 표시한다. 정확한 신호는 클라이언트가 `request_tags`에 상태를 실어야 얻어진다 — v1.5 요구사항으로 등록.

### 7.3 사용자 식별 전제 — 검증 필요

LiteLLM에서 개인 단위 집계가 성립하려면 `user` 또는 개인별 `api_key`가 세팅되어 있어야 한다. **팀 공용 키를 쓰는 환경이면 개인 차량 개념 자체가 불가능하다.** v1은 시뮬레이터라 영향 없으나, 실데이터 전환 전 반드시 확인해야 하는 차단 조건이다. → §13 미해결 질문 Q1.

## 8. 시뮬레이터 요구사항

v1의 유일한 데이터 소스. **동시에, v1이 실패할 가장 큰 원인이기도 하다.**

가짜 데이터가 재밌게 만들어질수록 실데이터 전환 시 배신당한다. 실제 에러율이 0.5%면 라디오는 종일 침묵하고, 200명이 다 조용하면 화면은 텅 빈다.

### 8.1 필수 요구사항

| # | 요구사항 |
|---|---|
| SIM-1 | 모든 이벤트 확률·분포를 **설정 파일로 노출**한다. 코드에 상수 하드코딩 금지 |
| SIM-2 | 프리셋 최소 3종: `busy`(활발한 조직), `sparse`(대부분 조용), `chaos`(에러 다발) |
| SIM-3 | `sparse` 프리셋에서도 화면이 죽지 않는지 검증한다. **이것이 기본 검수 시나리오** |
| SIM-4 | 시간 배속 지원 (1× / 60× / 600×). 8시간 레이스를 48초에 검증 |
| SIM-5 | **시드는 트랙 맵 코스 생성에만 사용한다.** 차량·상태·이벤트·라디오·카메라 선별은 이벤트 데이터로만 결정한다 (§15 확정). 실행마다 새 시드를 생성하되, 세션 스냅샷에 시드를 저장해 같은 코스를 재현할 수 있게 한다 |
| SIM-6 | `EventSource` 인터페이스 뒤에 위치. 실 어댑터와 교체 가능 |

### 8.2 기본 분포 (설정값, 실측으로 대체 예정)

| 파라미터 | 기본값 | 근거 |
|---|---|---|
| 동시 활동률 | 15% | 추정 **[Low]** — 실측 필요 |
| 호출 간격 | 로그정규 (중앙값 45s) | 추정 **[Low]** |
| 에러율 | 1.5% | 추정 **[Low]** |
| 캐시 히트율 | 40% | 추정 **[Low]** |
| 지연시간 | 로그정규 (중앙값 3.2s) | 추정 **[Low]** |

> 전부 `[Low]` 신뢰도다. 이 숫자들은 실측 전까지 **아무것도 증명하지 않는다.** 실 LiteLLM 로그 1일치를 확보하는 즉시 교체한다.

### 8.3 백로그 — OpenF1 모션 베이스

움직임이 어색할 경우의 카드. OpenF1 API가 2023년 이후 히스토리컬 데이터를 무료·무인증 제공한다(무료 티어 3req/s · 30req/min, 실시간만 유료). 실제 레이스 한 판의 차량 위치 시계열을 모션 베이스로 깔면 추월·간격 변화·피트 타이밍의 리듬이 진짜에서 온다. **v1 필수 아님.**

## 9. 디렉터 로직 (카메라 선별)

### 9.1 스코어링

```
score(car) = Σ wᵢ · signalᵢ(car)
```

| 신호 | 기본 가중치 | 설명 |
|---|---|---|
| 에러 발생 | 100 | 최근 30초 내 |
| 한도 임계 도달 | 80 | 연료 < 한도 경고 잔여 임계값(기본 20%). **타이어 모드가 `off`가 아닌 경우에만** 타이어 < 15%를 함께 본다 |
| 비용 급등 | 60 | 개인 이동평균 대비 3σ 초과 |
| 지연 이상 | 40 | 전체 분포 p95 초과 |
| 침묵 후 재가동 | 30 | 10분 이상 유휴 후 첫 호출 |
| 마일스톤 | 20 | 누적 거리 라운드 넘버 통과 |
| 핀 고정 | +∞ | 사용자 지정 |

> **타이어 기본값이 `off`이므로 v1 기본 상태에서 "한도 임계 도달"은 연료 단독 판정이다 [High].** 신호가 하나 줄어드는 만큼 `sparse` 프리셋에서 점수 있는 차량이 0대가 될 확률이 올라간다. §9.2 빈 슬롯 폴백이 그래서 필수다.

### 9.2 안정화 규칙 — 깜빡임 방지

> 자동 선별 UI가 실패하는 방식은 언제나 같다: 너무 자주 바뀌어서 읽을 수 없다.

| 규칙 | 값 |
|---|---|
| 최소 노출 시간 | 8초 (점수가 떨어져도 유지) |
| 동일 차량 재선별 쿨다운 | 60초 |
| 슬롯 교체 최소 간격 | 3초 (전체 슬롯 동시 교체 금지) |
| 빈 슬롯 폴백 | 최근 활동량 상위 |

`sparse` 프리셋에서 점수 있는 차량이 0대여도 슬롯은 폴백으로 채워진다. 빈 카드는 화면을 죽인다.

## 10. 팀 라디오

### 10.1 두 종류

**이벤트 라디오 (즉시).** 에러, 리타이어, 피트 인/아웃, 한도 임계. 트리거 즉시 발화.

**루틴 라디오 (정시).** 매시 정각, 개인당 최대 1건. 직전 1시간 메타데이터에서 패턴 도출.

### 10.2 루틴 라디오 규칙 세트 (v1)

| 조건 | 메시지 |
|---|---|
| `cache_hit` 비율 < 20% (직전 1시간) | "캐시 미스가 잦음. 컨텍스트가 매번 바뀌고 있음." |
| 평균 프롬프트 토큰이 개인 기준선 2배 초과 | "프롬프트가 무거워지고 있음. 컨텍스트 정리 권장." |
| 상위 티어 모델로 단문 호출 반복 | "짧은 작업에 상위 클래스 사용 중." |
| 에러 3회 이상 반복 | "같은 구간에서 반복 실패. 접근을 바꿔볼 것." |
| 해당 없음 | 발화하지 않음 (침묵은 정상) |

### 10.3 하드 제약

- **메시지는 전부 메타데이터에서 생성한다.** 프롬프트·응답 본문을 읽지 않는다. LLM으로 문장을 만들지 않는다 — v1의 라디오는 룰 기반 템플릿이다.
- 동일 유형 메시지 30분 내 재발화 금지.
- 톤은 오퍼레이터. 평가나 훈계가 아니라 관측 보고.
- **비교 금지.** "다른 사람보다 캐시를 덜 쓴다" 류의 문장은 생성하지 않는다. 본인 과거 기준선과만 비교한다.

### 10.4 일일 브리핑 (레이스 후) — 신규

§7.2.1 결과로 캐시 토큰 인사이트가 여기로 이동한다. 18:00 체커기 직후 하루 요약 카드(S4)에 함께 표시한다.

| 조건 | 메시지 |
|---|---|
| `cache_read_input_tokens` / `prompt_tokens` < 20% | "오늘 캐시 읽기 비율 12%. 같은 컨텍스트를 반복 전송했음." |
| `prompt_caching_savings_spend` > 0 | "캐싱으로 $X 절감." |
| `failed_requests` / `api_requests` > 5% | "실패율 7%. 어제보다 높음." |

일별 집계 테이블 1회 조회로 전부 해결된다. 실시간 경로에 부담을 주지 않는다.

### 10.5 백로그 — TTS

경량 오픈소스 TTS로 실제 무전 음성. v1 제외. 텍스트 라디오의 유용성 피드백이 30%를 넘으면 착수한다.

## 11. 렌더링 및 성능

### 11.1 기술 결정

`matteocelani/f1-telemetry`가 동일 문제를 유사하게 풀었다 — **SVG + `requestAnimationFrame` 60fps 보간 + 직접 DOM 조작. WebGL·canvas 불필요.** 그리고 이벤트를 **50ms 윈도우로 배칭**해 전송한다.

> **v1.2 원본 코드 확인 결과 (`877f99c`, 2026-06-03). 상세는 [f1-telemetry 분해 문서](../../reference/2026-07-30-f1-telemetry-teardown.md).**
>
> - **직접 DOM 조작은 `TrackMap`의 rAF 핫패스 한 곳뿐이다 [High].** 나머지 UI는 Next.js 16 + React 19 + zustand로 렌더한다. 프론트엔드 런타임 의존성 28개. **이 저장소는 §11.4의 "UI 프레임워크 없음" 결정을 지지하지 않는다** — 그 결정의 근거는 우리 자체 논리(200노드 직접 조작 + 의존성 0)뿐이다.
> - **50ms 배칭은 서버 측이다 [High]** (`socket-server.ts`). 채널별 최신값으로 접고(deep merge) 직렬화 diff로 무변경 채널을 건너뛴다. v1에 서버가 없으므로 같은 배칭을 `EventSource` → 스토어 경계에 둔다.
> - **위치 지정은 좌표 계산이 아니라 CSS `offset-path` + `offset-distance`다 [High].** rAF가 프레임마다 쓰는 것은 퍼센트 문자열 하나뿐이다. 채택 검토 대상 — 단 jsdom이 계산하지 못하므로 순수 함수 `positionAt()`은 테스트용으로 유지한다.
> - **보간은 앵커 + 전방투영 + lerp 3단이며, 투영을 0.95에서 클램프한다 [High].** 데이터가 늦어도 차가 다음 앵커를 앞질러 가지 않는다. §15의 "데이터 없을 때 임의 이벤트 생성 금지"와 같은 규율. **그대로 채택한다.**
>
> **권위 재평가 [Medium].** 별 수는 실측대로 38★(최종 푸시 2026-06-03), `sab-f1-ui`는 24★·2022-03-29 방치가 맞다. 다만 `f1-telemetry`의 코드는 취미 수준 이상이다 — 핫패스 무할당, NaN 가드, "F1이 랩 카운트 증가 전에 세그먼트를 0으로 리셋한다"는 실전 결함 대응이 들어 있다. **"합리적 출발점"에서 "검증할 가치가 있는 구현 디테일 출처"로 상향한다.** 자체 벤치마크를 릴리스 게이트로 두는 것은 그대로 유지한다(§11.2).

세 번째가 우리에게 특히 중요하다. **실제 위치는 띄엄띄엄 오는데 화면은 매끄러워야 한다.** F1도 마이크로섹터 앵커 사이를 보간으로 메운다. LiteLLM 로그도 호출 단위로 띄엄띄엄 온다 — 같은 구조, 같은 해법.

### 11.2 성능 예산

| 항목 | 예산 |
|---|---|
| 프레임률 | 60fps (2020년급 내장 GPU 노트북) |
| 차량당 DOM 노드 | ≤ 3 (본체 / 클래스 링 / 이벤트 펄스) |
| 총 SVG 노드 | ≤ 800 |
| 프레임당 갱신 | `transform` / `opacity`만. 레이아웃 유발 속성 변경 금지 |
| 이벤트 배칭 | 50ms 윈도우 |
| 이벤트 버퍼 | 링버퍼 고정 크기 (기본 2,000건) |

> **[Medium]** 200개 SVG 노드를 `transform`만으로 60fps 갱신하는 것은 브라우저에 부담이 아닐 것으로 판단하나, **자체 측정 전이므로 [High]로 주장하지 않는다.** 위험은 노드 수가 아니라 **레이아웃 유발 속성**(`x`, `y`, `width`, `cx`, `cy` 직접 변경)이다.
>
> **릴리스 게이트: 200노드 · 60fps · 8시간 연속 구동 벤치마크를 자체 측정하고 수치를 기록한다.** 측정 없이 통과 선언하지 않는다.

### 11.3 상시 노출 대응 — 8시간 실행의 현실

> 30년차 규칙: 8시간 띄워둘 물건은 8시간 띄워두고 테스트해야 한다. 5분 데모에서는 아무 문제도 안 보인다.

| 문제 | 대응 |
|---|---|
| 이벤트 배열 무한 증가 | 링버퍼 고정 크기. 초과분 폐기 |
| DOM 노드 누수 | 차량 노드는 풀링. 생성/삭제 대신 재사용 |
| 백그라운드 탭 `rAF` 정지 | `visibilitychange`에서 상태 재동기화. 복귀 시 보간 건너뛰고 스냅 |
| 절전 복귀 후 시계 점프 | 타임라인은 벽시계 기준 재계산. 경과 시간 누산 금지 |
| 메모리 증가 | 8시간 연속 실행 시 힙 증가 ≤ 50MB. 릴리스 게이트 |

### 11.4 스택

|---|---|---|
| 빌드 | Vite + TypeScript | |

## 12. 프라이버시 · 윤리 가드레일

**이 절은 협상 대상이 아니다.** 나중에 뺄 수 없는 것들만 모았다.

| # | 규칙 |
|---|---|
| PRIV-1 | **기본 익명.** 트랙 위 모든 차량은 카넘버 + 클래스로만 표시. 이름 없음 |
| PRIV-2 | **이름 비표시.** 개인 차량은 카넘버와 설정된 메타데이터로만 표시하며, 자체 회원가입·필수 로그인은 제공하지 않음 |
| PRIV-3 | `car_id = HMAC(user_id, deployment_salt)`, **어댑터 측(서버)에서 계산**. 원본 식별자는 프론트엔드 경계를 넘지 않음. v1 시뮬레이터는 원본 식별자가 애초에 존재하지 않으므로 `car_id`를 직접 생성한다 |
| PRIV-4 | **프롬프트·응답 본문 미수집.** 스키마에 필드 자체가 없음 |
| PRIV-5 | **개인 간 정렬·순위 UI 금지.** 타이밍 타워를 만들지 않는다. 카메라 선별은 "사건성" 기준이지 성과 기준이 아니다 |
| PRIV-6 | 연봉 HUD는 `localStorage`에만 저장. 서버 전송 금지. 로컬 설정으로 활성화한 화면에서만 렌더 |
| PRIV-7 | 관리자 실명 모드는 v1에 **없다.** 의도적 부재이며, 추가 요청 시 §3.2 반증 지표로 취급 |
| **PRIV-8** | **어댑터는 명시적 컬럼 화이트리스트로만 조회한다. `SELECT *` 금지.** 아래 사유 참조 |

### 12.0 PRIV-8의 사유 — 신규 리스크 [High]

원본 스키마 확인 결과 `LiteLLM_SpendLogs`에 다음 컬럼이 **존재한다**:

- `messages` (Json) — 요청 프롬프트 본문
- `response` (Json) — 응답 본문
- `requester_ip_address` — 요청자 IP
- `proxy_server_request` (Json) — 원본 요청 전체

즉 **LiteLLM 설정에 따라 프롬프트·응답 본문과 IP가 이미 DB에 저장되어 있을 수 있다.**

v1.0의 PRIV-4는 "우리 스키마에 필드가 없다"고만 규정했다. 이는 불충분하다 — 어댑터가 `SELECT *`를 한 줄 쓰는 순간 본문 전체가 애플리케이션 메모리로 들어오고, 로그·에러 리포트·메모리 덤프를 통해 유출될 수 있다. **"안 쓴다"와 "안 가져온다"는 다르다.**

허용 컬럼 화이트리스트(v1.5 어댑터):
`request_id`, `api_key`, `user`, `team_id`, `model`, `model_group`, `spend`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `startTime`, `completionStartTime`, `request_duration_ms`, `cache_hit`, `status`, `session_id`, `request_tags`

**허용 파생 표현 1개.** 오류 코드는 컬럼이 아니므로 컬럼 화이트리스트로 표현할 수 없다. **DB 쿼리에서 단일 스칼라로 뽑아내는 표현만** 허용한다.

```sql
-- 허용: JSON 경로 하나를 스칼라로 추출. metadata 원문은 애플리케이션에 도달하지 않는다
metadata ->> 'error_code' AS error_code

-- 금지: 원문 반입 후 애플리케이션에서 파싱
metadata
```

추출한 값은 §16 Q6에서 확정할 정규화 목록에 없으면 버리고 `error_code`를 비운다. **JSON 경로와 정규화 목록이 확정되기 전에는 이 표현을 쓰지 않고 `error_code`를 항상 비워 둔다** — 경로를 모르는 상태로 `metadata ->> '???'`를 짐작해 쓰는 것이 이 규칙이 막으려는 바로 그 행동이다.

**명시적 금지:** `messages`, `response`, `proxy_server_request`, `requester_ip_address`, `cache_key`, `api_base`, **`metadata` 원문**(위 파생 표현 1개 외 일체).

> **v1.3 정정 [Medium].** v1.3 산문은 "쿼리 계층에서 오류 코드만 추출한다"고 했으나 화이트리스트에는 그 표현이 없었다. 산문과 화이트리스트가 다른 말을 하면 코드 리뷰(REM-11)가 무엇을 통과시켜야 하는지 판정할 수 없다. 표현을 명시적으로 등재해 해소한다.

### 12.1 잔여 리스크 — 재식별

**[Medium]** 익명화해도 소규모 팀에서는 카넘버 + 시간 패턴으로 개인 특정이 가능하다. "점심시간에 안 쉬는 유일한 차", "매일 10시에 출발하는 차". k-익명성이 깨지는 조건이다.

완화: 팀 인원이 **최소 집계 인원(k)** 미만인 배포에서는 개인 차량 모드를 강제로 비활성화하고 팀 단위 집계만 표시한다.

**k = 10. 상향만 가능하고 하향은 불가능하다.** 설정 파일에 `k = 3`을 써도 런타임이 10으로 되돌린다.

> **v1.3 후퇴 정정 [High].** v1.3은 "강제로"라는 단어를 넣으면서 동시에 k를 "조직 보안 정책의 하한선 아래로 낮출 수 없다"로 바꿨다. **`조직 보안 정책의 하한선`은 이 문서 어디에도 정의가 없다.** 정의 없는 외부 참조를 하한으로 삼으면 하한이 없는 것과 같다 — v1.2의 하드코딩 10보다 약해졌다. 문구는 강해지고 보장은 약해진 변경이며, A2(최고 위험)의 유일한 정량 방어선에서 발생했다. 상수 10을 코드 하한으로 되돌린다.

완전 해결은 불가능하며, 이 한계를 문서화한 채로 출시한다.

### 12.2 법적 전제 — 실데이터 전환 시 발생

**[Medium]** 근로자 활동 모니터링은 관할에 따라 사전 고지·동의 의무가 발생할 수 있다 (한국 개인정보보호법, EU GDPR). v1은 시뮬레이터라 무관하나, **실 LiteLLM 연동은 법무 검토 없이 진행하지 않는다.** v1.5 착수 조건으로 등록.

### A21의 사유 — 지표와 아키텍처의 충돌 [High]

§3.1은 "주 3일 이상 실행하는 사용자 비율 ≥ 40%", "1인당 일평균 정상 실행·가시 상태 시간 ≥ 2시간"을 4주차에 측정한다고 적었다. 그런데 §11.4는 **백엔드 없음**, PRIV-6은 **로컬 저장·서버 전송 금지**다.

**여러 사용자에 걸친 실행 시간을 모으려면 수집 엔드포인트가 필요하고, v1에는 그것이 없다.** v1.3이 지표 이름을 "노출 시간 → 정상 실행·가시 상태 시간"으로 정직하게 바꾸면서 이 구멍이 더 선명해졌다 — 이름이 정확해져도 측정 수단은 여전히 없다.

선택지는 셋이다. **어느 것도 v1.4에서 결정하지 않는다 — Q8로 등록한다.**

1. 4주차 측정을 자기보고(설문)로 대체하고 §3.1을 그렇게 명시 — 정직하지만 데이터 질이 낮다
2. 익명 텔레메트리 엔드포인트 1개를 v1에 추가 — PRIV-6·§12.2와 충돌. **감시 도구화 인상을 주는 순간 A2가 발동한다**
3. 지표를 로컬 자기 관찰로 축소(본인 화면에만 "이번 주 N일 실행") — 조직 단위 판정 불가

> 이 리스크는 v1.3이 만든 것이 아니라 v1.0부터 있었다. 지표 문장이 세 번 다듬어지는 동안 아무도 "이걸 어떻게 수집하는가"를 묻지 않았다. 등록만 하고 넘기지 않기 위해 Q8을 §14 v1 착수 전 결정 항목으로 둔다.

## 15. 승인 확정사항 (MVP)

### 제품 접근과 식별

- PITWALL은 회원가입을 요구하지 않는다.
- AI 서비스별 재로그인은 필수가 아니며, 필요한 경우 1회 인증 후 세션을 재사용한다.
- 기본 식별자는 기존 LiteLLM 로그의 `user` 또는 개인별 `api_key`다. `team_id`는 팀 집계에 사용한다.
- 공용 키만 있는 환경에서는 개인 차량 대신 팀 차량으로 표시한다.
- 이름은 표시하지 않으며, 원본 식별자·API 키·프롬프트·응답 본문은 브라우저에 전달하지 않는다.

### 표시와 상호작용

- 이름을 제외한 개인 차량 정보는 제공하되, 트랙에는 핵심 상태만 표시하고 상세값은 카메라 카드·선택 영역에서 계층적으로 표시한다.
- 하이라이트는 이벤트 유형별 ON/OFF 옵션으로 제공한다. 기본값은 오류·한도·지연 이상 중심이다.
- 카메라는 기본 3개, 최대 5개이며 핀 고정이 자동 선별보다 우선한다.
- 라디오 문구는 F1 팀 라디오의 압축된 명령형·감정형 톤에서 영감을 얻되 실제 문구·음성은 복제하지 않는다.
- `ehvkals` 입력 시 도파민 이스터에그를 실행하며, 짧은 음원 재생은 사용 허가 또는 라이선스가 확보된 경우에만 활성화한다.

### 시뮬레이터와 세션

- MVP 데이터 소스는 더미 데이터 기반 시뮬레이터다. 실시간 LiteLLM 연동은 MVP 범위에서 제외한다.
- `busy`는 출근 포메이션 랩과 카운트다운 후 즉시 주행을 시작한다. 기본 배속은 1×이며 `sparse`+600×는 검수 시나리오로 사용한다.
- 실행마다 새 시드를 생성한다. 시드는 트랙 맵 코스 생성에만 사용하며, 차량·상태·이벤트·라디오·카메라 선별은 이벤트 데이터에 의해서만 결정한다.
- 새 레이스는 출근, 이어하기는 세션 재개다. 최근 5개 세션과 당시 시드·설정 스냅샷을 로컬에 저장한다.
- 랜덤 맵은 유효성 검사 후 사용하며, 시작점·피트·섹터·진행 방향과 레인 가독성을 보장한다.
- 이벤트 보간은 수신된 이벤트 사이에서만 수행한다. 데이터가 없을 때 임의 이벤트를 생성하지 않는다.
- 데이터 수집 중단(`STALE`)과 토큰·비용 한도 초과(`LIMITED`)를 별도 상태로 표시한다. 한도 초과는 무한 재시도하지 않는다.

### 설정·운영·검수

- 출퇴근·휴식시간, 레이스 길이, 배속, 한도 경고, 타이어 모드, 하이라이트, 모션, 사운드, 레이아웃은 옵션이며 로컬에 저장한다. 조직 기본값은 공유 설정 파일로 제공한다. 설정 우선순위는 조직 기본값 → 사용자 로컬 설정 → 현재 세션 설정이다.
- 기본 화면은 한국어이며 핵심 레이싱 용어는 영어를 병기한다.
- MVP 공식 지원은 최신 Chrome의 macOS·Windows다. 정적 페이지로 배포하고, 로드 후 시뮬레이터는 오프라인에서도 실행한다.
- MVP 출시 게이트는 `busy / sparse / chaos` 동작, 상태 구분, 세션 새로 시작·이어하기, 이스터에그, 접근성 옵션, 8시간 실행 안정성 수동 검수다.

| 연료 | 일간 예산 잔여 |
| 타이어 | 선택된 타이어 모드의 잔여율. 기본 `off` (§7.0) |
| 카메라 | 자동 선별되는 확대 표시 슬롯 |
| 디렉터 | 카메라 선별 로직 |
| 라디오 | 이벤트·인사이트 메시지 채널 |
| 피트 | 유휴 상태 |

## 19. 잔여 검수 항목

아래 항목은 시뮬레이터 MVP의 출시를 막지는 않지만, 실 LiteLLM 연동과 v1.5 착수 전에 반드시 확인하고 결과를 기록한다.

| ID | 검수 항목 | 합격 기준 | 결과 기록 |
|---|---|---|---|
| REM-1 | 개인 식별자 가용성 | `user` 또는 개인별 `api_key`가 실제 로그에서 확인됨. 공용 키 환경은 팀 차량 모드로 전환 | Q1 결과 첨부 |
| REM-2 | 실제 이벤트 분포 | 활동률·에러율·호출 간격·캐시율·지연시간을 최소 1일 로그로 산출하고 시뮬레이터 기본값과 비교 | Q2 결과 첨부 |
| REM-3 | 예산·한도 출처 | 일간·주간 한도의 출처, 갱신 주기, 계산 지연, `fuel_pct` 산식을 확정 | Q3 결과 첨부 |
| REM-4 | 모델 프로필 매핑 | H/P/GT, `reasoning_level`, `context_window` 매핑 기준과 변경 이력을 설정 파일로 관리 | Q4 결과 첨부 |
| REM-5 | 근무시간 정책 | 우선순위는 §7.0에서 확정(Q5 해소). **남은 검수 대상은 근무 창 밖에 도착한 이벤트의 처리**와 조직 기본값 파일의 실제 배포 경로 | 운영 리허설 결과 |
| REM-6 | 데이터 계약 검증 | `event_id`, `ts`, 중복·지연 이벤트, 누락 필드, 상태 전이 규칙을 실제 어댑터로 검증 | 어댑터 테스트 결과 |
| REM-7 | 한도 초과 처리 | 일시적 429와 실제 한도 초과를 구분하고, 무한 재시도 없이 리셋 시점 재확인이 동작 | 장애 시나리오 결과 |
| REM-8 | 프라이버시·접근 통제 | 원본 식별자·API 키·프롬프트·응답 본문이 프론트엔드와 로그에 노출되지 않음 | 보안 검수 결과 |
| REM-11 | **PRIV-8 컬럼 화이트리스트** | 어댑터 쿼리에 `SELECT *`가 없고, `messages`·`response`·`proxy_server_request`·`requester_ip_address`가 조회 대상에서 제외됨 (§12.0) | 코드 리뷰 결과 |
| REM-9 | 법무 승인 범위 | 개인 차량 표시, 비용·토큰 표시, 보존 기간, 관리자 접근 범위가 승인 문서와 일치 | 승인 문서 링크 |
| REM-10 | 운영 안정성 | 데이터 끊김(`STALE`), 한도 초과(`LIMITED`), 복구·재연결·세션 이어하기가 실제 환경에서 검증됨 | 운영 리허설 결과 |
