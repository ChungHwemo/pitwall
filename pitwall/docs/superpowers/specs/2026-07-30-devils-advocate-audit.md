## 0. 결론 먼저

MVP는 **자기가 표방한 목적을 달성하지 못한다.** "곁눈질로 조직의 LLM 사용을 읽는다"가
목표인데, 화면에 있는 숫자로는 지금 빠른지 느린지, 돈이 얼마나 나갔는지, 언제 막히는지를
답할 수 없다. 같은 데이터를 다루는 오픈소스 도구들은 이 셋을 **첫 화면 첫 줄**에 둔다.

## 1. 비교 대상이 첫 화면에 두는 것

동일한 로컬 로그를 읽는 도구들이다. 기능 목록은 각 저장소 README·문서에서 확인했다.

| 도구 | 첫 화면에 있는 것 |
|---|---|
| **ccusage** `statusline` | 세션 비용($), 오늘 누적 비용($), 현재 5시간 블록 비용 + **남은 시간**, **소진 속도**(토큰/분), 활성 모델 |
| **ccusage** `blocks --live` (v17) | 진행 바, 소진 속도, 5시간 블록 잔여 시간, **비용 예측**, 색상 경고, 1초 갱신 |
| **Claude-Code-Usage-Monitor** v4 | 공식 `rate_limits`, **출처 라벨**(`official`/`local_estimate`/`experimental`/`unknown`), 리셋 기준 페이스, **예측**, 주간 %, 한도 도달 시 고정 |
| **sniffly** | 사용 패턴 통계, **에러 유형별 분해**, 메시지 히스토리 워크스루 |
| **vibe-log** | 오늘의 스탠드업, 생산성 리포트 |

공통점: **속도 · 돈 · 리셋까지 남은 시간**. 셋 다 PITWALL에 없다.

## 2. 교차검증 — 결손 항목

### F1. 근무창 가정이 데이터와 어긋난다 (치명)

레이스는 09:00–18:00에서 점심을 뺀 8시간이다. **오늘 작업의 61.4%가 이 창 밖에서
발생했다.** 시간대별로:

```
09시  466k   ████
13시  1.21M  ████████████
17시  1.44M  ███████████████
18시  3.73M  ███████████████████████████████████████   ← 하루의 33%
20시  1.90M  ████████████████
```

가장 굵은 두 시간대(18시·20시)가 통째로 레이스 밖이다. 화면이 절반 이상의 사실을
버리고 있다. 비교 대상들은 상상 속 근무시간이 아니라 **Anthropic이 실제로 굴리는
5시간 롤링 블록**에 맞춘다.

PRD가 "8시간 근무"를 전제로 잡았고, 나는 그 전제를 실데이터로 검증하지 않은 채
구현했다.

### F2. 화면에 돈이 없다

오늘 $401.63을 썼는데 화면에 달러 표시가 **한 글자도 없다.** 대신 `FUEL 93%`가 있다.
그 93%의 분모는 `dailyBudgetUsd = 60` — 아무도 설정한 적 없는 기본값이다.

게다가 그 게이지는 **10:01에 0%에 도달하고 그 뒤 호출의 73%가 연료 0으로 찍힌다.**
하루의 4분의 3 동안 "연료 없음"을 표시하는 게이지는 게이지가 아니다.

ccusage는 세션 비용·오늘 비용·블록 비용을 각각 달러로 먼저 보여준다.

### F3. 소진 속도가 없다

비교 대상 전부가 토큰/분 또는 $/시간을 보여준다. PITWALL은 **누적값만** 보여준다
(`WORK 52.5k · CACHE 6.6M`). 실측 속도는 Claude 6,462 work토큰/분, $18.02/시간인데
어디에도 없다.

앰비언트 디스플레이가 답해야 하는 질문은 "지금 빠른가"이고, PITWALL은 못 답한다.

### F4. 리셋 시각을 가지고 있으면서 버린다

`fixtures/limits.json`에 `resets_at`이 들어 있다. 화면은 `LIMIT 81%/5시간`만 쓰고
언제 풀리는지는 안 쓴다. ccusage는 "블록 잔여 시간"을, Monitor는 리셋 기준 페이스와
예측을 보여준다. **잔여 %만으로는 행동을 못 정한다** — 10분 뒤 리셋이면 기다리고,
4시간 뒤면 모델을 바꿔야 한다.

### F5. 출처·신선도 라벨이 없다

Monitor v4의 대표 기능이 출처 라벨이다. PITWALL은 화면에서:

- Claude 한도 = 방금 API에서 받은 값
- Grok 한도 = **6일 전** 로그에서 주운 값

둘을 **똑같은 서체로 똑같이** 렌더한다. 나는 CLI 출력에는 "판독 6일 전"을 찍어놓고
화면으로 넘기기 전에 그 정보를 버렸다.

### F6. 에러 화면이 없다

sniffly의 두 번째 기능이 에러 유형별 분해다. PITWALL은 오늘 에러가 0건이라 아무것도
안 뜨고, 에러가 나도 차 위에 글리프 하나가 뜰 뿐이다. 유형도, 누적도, 이력도 없다.

### F7. 시계가 가짜다

상단이 `02:56:00 / 08:00:00 · DEMO`, 배속 60×. **날짜가 없고 실제 시각도 없다.**
차의 위치가 지금과 무슨 관계인지 화면만 봐서는 알 수 없다. 비교 대상은 전부 벽시계에
고정돼 있다.

### F8. 화면을 지배하는 숫자가 죽은 숫자다

캐시 재전송이 전체 토큰의 98.4%(696M)다. 거리는 작업 토큰만 센다 — 이 선택 자체는
옳다(캐시는 일이 아니다). 그러나 결과적으로 카드에서 가장 큰 숫자(`CACHE 6.6M`)가
아무 움직임도 만들지 않는 장식이 된다. 큰 숫자와 움직임이 따로 논다.

### F9. 군중 제어가 전부 죽은 코드

`HOT_CAP = 12`, `LANE_RENDER_CAP = 40`, 클러스터 오버플로, k≥10 익명성 하한 —
수십 계정 조직을 가정한 장치다. 실제 계정 수는 **2대**다. 트랙의 90%가 비어 있고
밀도 조절 코드는 한 번도 발동하지 않는다.

### F10. 라벨이 없어 클릭해야 안다

트랙 위 차에는 아무 글자도 없다. 어느 계정이 무슨 모델을 돌리는지 알려면 클릭해야
한다. **상호작용을 요구하는 앰비언트 디스플레이는 앰비언트가 아니다.**

## 3. 내가 이 턴에 세웠다가 틀린 가설

"랩이 20만 토큰이라 차가 안 돈다"고 먼저 의심했다. **틀렸다** — 실측 40.6바퀴/일이다.
화면에서 차가 안 움직여 보인 진짜 이유는 F1이다: 작업의 61%가 레이스 창 밖이고,
창 안에서도 앞부분이 비어 있어 재생 초반에 거리가 거의 안 쌓인다.

## 4. 우선순위

측정된 결손을 영향도 순으로 놓는다.

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | **F1** 근무창 → 실제 활동 창(또는 5시간 롤링 블록)으로 교체 | 사실의 61.4%가 화면 밖 |
| 2 | **F2 + F3** 돈과 속도를 첫 줄로 | $401·$18/시간·6.5k토큰/분이 전부 미표시 |
| 3 | **F7** 실제 날짜·시각 표시, DEMO 배속 기본 해제 | 위치의 의미가 붕괴 |
| 4 | **F4** 리셋까지 남은 시간 | 데이터를 이미 갖고 있음 |
| 5 | **F5** 출처·신선도 라벨 | 6일 전 값과 실시간 값을 구분 못 함 |
| 6 | **F10** 트랙 위 라벨 | 클릭 없이 읽히게 |
| 7 | **F6** 에러 유형 표시 | 현재 데이터로는 검증 불가(에러 0건) |
| 8 | **F9** 군중 제어 축소 | 죽은 코드, 화면 낭비 |

F8은 표시 방식의 문제라 F2 해결 시 함께 정리된다.
